# Обновление ITK CMS

## Как обновить сайт

Делайте шаги по порядку, сначала на копии сайта:

1. Прочитайте [CHANGELOG.ru.md](CHANGELOG.ru.md) за все версии между вашей и целевой, а также заметки к версиям в конце этого файла.
2. Включите режим обслуживания и заблокируйте приём форм в окружении, где сейчас работает сайт. При переходе 0.2.2 → 0.3.0 оставьте воркеры 0.2.2 работать до опустошения очереди, включая отложенные повторы. Проверьте очередь командой `bin/console messenger:stats` и подтвердите **0** проверкой, которая учитывает отложенные и обрабатываемые сообщения. Для Doctrine посчитайте все строки `messenger_messages` (или настроенной таблицы) по `queue_name`. Разберите сообщения в очереди ошибок до продолжения. Затем остановите воркеры и остальные процессы записи в базу или загрузки и только после этого сделайте резервную копию базы данных и загруженных файлов. Если переходите со своей схемы развёртывания на комплект 0.3.0, следуйте разделу [Первый переход на production-комплект](#первый-переход-на-production-комплект).
3. Укажите в `composer.json` сайта ограничение для целевой минорной версии. При переходе с 0.2.x на 0.3.0 замените `"itk/cms": "~0.2.0"` на `"itk/cms": "~0.3.0"`. Версии 0.3.0 нужны Symfony 7.4.23 или новее (либо 8.1 и новее), Doctrine ORM 3.8 и DBAL 4.6, поэтому обновляйте зависимости вместе с бандлом. В комплекте для разработки выполните `docker compose exec php composer update itk/cms --with-all-dependencies` и проверьте версию командой `docker compose exec php composer show itk/cms`. Для production обновите `composer.lock` сайта в исходниках релиза. Если используете production-комплект, соберите оба образа из этого релиза — приложение и nginx с ассетами админки. Проверьте установленную версию в новом образе приложения и следуйте [порядку обновления в DEPLOY](docs/DEPLOY.ru.md#обновление).
4. Выполните миграции: `bin/console doctrine:migrations:migrate`. Миграции бандла (`Itk\Cms\Migrations`) выполняются вместе с миграциями сайта, в порядке дат в именах их классов.
5. В комплекте для разработки опубликуйте собранную админку командой `bin/console assets:install` и очистите кэш командой `bin/console cache:clear`. Symfony Flex публикует ассеты при `composer install` и `composer update`. В production-комплекте используйте ассеты из нового образа nginx.
6. Запустите службу воркеров очереди с новым релизом. Команда `bin/console messenger:stop-workers` просит работающие воркеры завершиться, но не запускает воркеры, остановленные до резервного копирования.
7. Проверьте сайт: выполните `bin/console itk:doctor` и `bin/console itk:schema:lint`, затем откройте админку и несколько страниц. Снимайте режим обслуживания и открывайте приём форм только после успешной проверки.

Если заметки к версии просят изменить конфигурационный файл сайта (например, `security.yaml`), сделайте это до шага 7.

## Версии

ITK CMS следует [семантическому версионированию](https://semver.org/lang/ru/spec/v2.0.0.html):

- Патч-релиз (0.1.1) содержит только исправления.
- Минорный релиз (0.2.0) добавляет возможности. Начиная с 1.0.0 он не ломает публичный API.
- Мажорный релиз (2.0.0) может ломать публичный API.

До версии 1.0.0 минорный релиз может ломать публичный API. Каждое такое изменение указано в [CHANGELOG.ru.md](CHANGELOG.ru.md) и в заметках к версиям ниже. Патч-релиз его никогда не ломает. Чтобы получать исправления без сюрпризов, закрепите в сайте минорную версию: `"itk/cms": "~0.3.0"`.

Изменения базы данных поставляются миграциями бандла. Бандл не меняет собственные таблицы сайта.

## Заметки к версиям

Здесь перечислены ручные шаги, которые нужны при обновлении на релиз, новые версии сверху.

### 0.3.0

#### Первый переход на production-комплект

В версии 0.3.0 появился необязательный комплект `compose.prod.yaml`. Вы можете сохранить свою схему развёртывания сайта. Сначала проверьте перенос и восстановление на копии: комплект не импортирует данные существующего сайта автоматически.

1. В старом окружении включите режим обслуживания и заблокируйте приём форм. Оставьте воркеры 0.2.2 работать до опустошения очереди, включая отложенные повторы. Проверьте очередь командой `bin/console messenger:stats` и подтвердите **0** проверкой, которая учитывает отложенные и обрабатываемые сообщения. Для Doctrine посчитайте все строки `messenger_messages` (или настроенной таблицы) по `queue_name`. Разберите сообщения в очереди ошибок до продолжения. Затем остановите воркеры и остальные процессы записи в базу или загрузки до резервного копирования. Сохраните **исходное развёртывание 0.2.2**: код или образы, Composer lock-файл, определения Compose/служб, конфигурацию прокси, настройки окружения и фактические расположения базы и загрузок. Скопируйте базу и фактический каталог или том загрузок в защищённое место вне контекста сборки. Пустые тома нового комплекта не заменяют эти источники. В архив загрузок положите содержимое каталога, который старый сайт отдаёт как `public/uploads`, с этим каталогом в корне архива (например, `tar -C <старый-сайт>/public/uploads -cf before-deploy-uploads.tar .`), чтобы `media/` оказался на верхнем уровне. При своём `upload_dir` распакуйте архив в соответствующий путь внутри `/app/public/uploads`.
2. Проверьте custom-format дамп через `pg_restore --list`. Для обычного SQL проверьте восстановление с `psql -v ON_ERROR_STOP=1`. Выведите содержимое архива загрузок и сравните число обычных файлов с исходным каталогом рекурсивно. Восстановите обе копии на тестовом стенде и проверьте записи сайта и несколько медиа. Читаемый архив ещё не доказывает, что сайт можно восстановить.
3. Подготовьте новый комплект по разделу [DEPLOY → Подготовка](docs/DEPLOY.ru.md#подготовка), соберите оба образа и запустите только `database`. При переносе базы восстановите её в **пустую целевую базу** комплекта до миграций. Имя задаёт `DEPLOY_DB_NAME` (по умолчанию `app`), внутри `database` это `POSTGRES_DB`. Имя базы должно совпадать с `DATABASE_URL`. Выберите команду по формату копии:

   ```sh
   # Custom-format: без --create, поскольку старое имя базы может отличаться.
   docker compose -f compose.prod.yaml exec -T database sh -c 'pg_restore --no-owner --no-privileges --exit-on-error -U postgres -d "$POSTGRES_DB"' < "$BACKUP_DIR/before-deploy.dump"
   # Альтернатива: обычный SQL от pg_dump --no-owner --no-privileges, без --create.
   docker compose -f compose.prod.yaml exec -T database sh -c 'psql -v ON_ERROR_STOP=1 -U postgres -d "$POSTGRES_DB"' < "$BACKUP_DIR/before-deploy.sql"
   ```

   Проверьте код завершения и запросом прочитайте несколько записей сайта в целевой базе. Если сохраняете внешнюю базу, используйте её подключение и прежний порядок резервного копирования и восстановления.
4. До запуска nginx восстановите загрузки в общий том `uploads` или подключите существующий каталог по пути `/app/public/uploads` для PHP и воркера, а для nginx — только для чтения. Штатная production-сборка задаёт PHP/воркеру `www-data` с **UID/GID `10033:10033`**. nginx работает как `10101:10101`. При переносе архива в новый том задайте владельца и права:

   ```sh
   docker compose -f compose.prod.yaml run --rm -T --no-deps --user 0:0 --entrypoint sh php -ec 'tar -C /app/public/uploads -xf - && chown -R 10033:10033 /app/public/uploads && chmod -R u+rwX,go+rX /app/public/uploads' < "$BACKUP_DIR/before-deploy-uploads.tar"
   ```

   Для bind mount каталога хоста задайте эквивалентного владельца или ACL. Проверьте, что PHP и воркер могут создать и удалить тестовый файл, а nginx — пройти по каталогам и прочитать старые файлы. Сверьте число восстановленных обычных файлов с источником. Если сайт меняет пользователей или аргументы сборки комплекта, подставьте его UID/GID.
5. Выполните миграции и обновите базовые настройки по разделу [DEPLOY → Обновление](docs/DEPLOY.ru.md#обновление), сохранив их вывод. Поднимите приложение, nginx и воркер в режиме обслуживания. Если миграция сообщила о коллизиях SEO-путей, найдите указанные ID в **Настройки → SEO → Правила адресов**. Для каждой коллизии перенесите нужные SEO-настройки в правило, которое оставляете, и удалите дубликат или задайте ему отдельный адрес. Сохраните оставленные правила **до открытия трафика**. Шаги из раздела [DEPLOY → Проверка](docs/DEPLOY.ru.md#проверка) включают `/healthz` и тестовое уведомление из очереди. Также откройте существующие медиа по HTTP и загрузите новое изображение через админку, чтобы проверить его сгенерированную копию. До переключения прокси проверьте [откат на исходное развёртывание 0.2.2](#откат-на-022).

#### Зарезервированные группы настроек

До запуска миграций выполните `itk:schema:lint` с версией 0.3.0 на копии сайта. Переименуйте группы сайта с ключами `menus`, `redirects`, `seo`, `notifications`, `mail`, `bots`, `theme`, `languages`, `users`, `mcp` и `seo-files` в `SchemaBuilder::settings()` или `SettingsResource::key()`. Обновите сохранённые права ролей и ссылки на права видимости полей на `set:<new-key>`. Оставьте прежние ключи полей, чтобы сохранить их значения.

#### Откат на 0.2.2

Миграции базы 0.3.0 несовместимы с кодом 0.2.2 и частично необратимы. Отката одного кода недостаточно.

1. Оставьте режим обслуживания и остановите все процессы записи 0.3.0. По конфигурации развёртывания 0.3.0 найдите и скопируйте текущую базу и загрузки. Храните эту копию отдельно от копии до обновления.
2. Восстановите базу **и** загрузки из копии до обновления в расположения сохранённого исходного развёртывания 0.2.2. Верните соответствующие код и образы, lock-файл, конфигурацию служб и прокси, настройки окружения. После первого перехода на комплект используйте для отката исходную конфигурацию служб.
3. До запуска любого воркера 0.2.2 проверьте восстановленную очередь, включая отложенные повторы и очередь ошибок (`messenger_messages` для Doctrine или внешний транспорт сайта). Сопоставьте конверты с итогами доставки в сохранённой копии 0.3.0 по ID заявки, каналу, ID задания при его наличии и адресу получателя для почты. Для повтора без ID задания проверьте по данным провайдера, дошла ли именно эта попытка. Удаляйте только отдельные конверты с подтверждённой доставкой в 0.3.0. Не допускайте обработку конвертов с неизвестным итогом до сверки доставки, при необходимости по данным провайдера. Иначе восстановленная старая очередь может повторить отправки, выполненные после резервного копирования.
4. Поднимите исходные службы, проверьте содержимое базы, `/healthz`, старые медиа и новую загрузку, затем откройте трафик через прежний прокси. Не подключайте 0.2.2 к мигрированной базе. Заявок, сохранённых 0.3.0 после открытия трафика, нет в копии до обновления: выгрузите их из сохранённой копии 0.3.0 (таблица `itk_request`, по времени создания) и перенесите или передайте вручную.

Для последующих обновлений сайта, уже работающего на комплекте, см. [DEPLOY → Откат](docs/DEPLOY.ru.md#откат). Храните этот порядок первого возврата вместе с резервной копией старого развёртывания.

#### Предложения ИИ

Удалите `->feature('ai')` из цепочки сборки схемы сайта, обычно в `config/itk/schema.php`. Панель предложений ИИ в редакторе и её флаг удалены.

#### Импорт строк в коллекции

Раньше `itk:make:collection --import` создавал записи коллекции из строк источника, а `--publish` публиковал их сразу. В 0.3.0 обе опции удалены, поле `rows` в JSON игнорируется. Класс по таблице или JSON-описанию создаётся как раньше. Переносите записи старого сайта своим скриптом или SQL вместе с дампом базы.

Ранее импортированные записи остаются в базе и редактируются как обычные записи коллекции. Ядро больше не читает их `meta.sourceId` и `meta.source`.

Запустите `bin/console itk:doctor` или откройте **«Состояние сайта»** и найдите проверку **«Устаревшие Twig-функции»**. Она проверяет `templates/`, показывает до десяти мест в формате `файл:строка` и число остальных совпадений. Команда `bin/console lint:twig templates` проверяет синтаксис. Из-за шаблона имён `render_*` Symfony может распознать старый вызов `render_sections()` при проверке синтаксиса, поэтому запустите также проверку старых вызовов.

Для быстрого поиска по тексту используйте команду ниже. В её выдачу могут попасть комментарии и строки.

```bash
grep -rnE --include='*.twig' '(^|[^[:alnum:]_])(menu|settings|listing|media_url|media_srcset|media_width|media_ratio|page_url|render_sections)[[:space:]]*\(' templates/
```

#### Другие изменения

- Поле **«Фотографии»** теперь добавляет из админки объекты `{src, alt}`, в том числе при пустом `alt`. Старые строки с URL остаются без изменений: в одном поле могут быть и строки, и объекты. Обновите шаблоны сайта до добавления новых фотографий редакторами; для каждого значения предусмотрите прежний формат:

  ```twig
  {% for p in photos %}
      <img src="{{ p.src ?? p }}" alt="{{ p.alt ?? '' }}">
  {% endfor %}
  ```

- `GET /admin/api/requests` и `GET /admin/api/media` вместо массивов возвращают `{ items, total, page, perPage, nextCursor, previousCursor }`. По умолчанию первая страница содержит до 50 строк. Если найдено соответствующее задание в транспорте ошибок, команда также напечатает команду с именем транспорта и ID задания. Эти команды работают без настроенного транспорта ошибок. Проверенный `sent` также фиксирует приём для старого общего предупреждения, даже если у адресата ещё нет отметки доставки. Старое общее предупреждение не закрывается автоматически: 0.2.2 не сохраняла полный исторический список получателей, а текущие и сохранённые старые маршруты его не доказывают. После независимой проверки всех исходных адресатов явно закройте старое общее предупреждение через `itk:requests:mail:resolve <request> --legacy-checked`. Флаг закрывает только общее предупреждение. Приём SMTP-сервером и доставка во входящие — отдельные шаги. Миграция необратима, поскольку удаление отметок могло бы повторно отправить принятые письма.
- Для писем о заявках `failover(...)` и `roundrobin(...)` могут перейти к другому серверу после подтверждённого отказа SMTP. Если сервер мог принять письмо, отправка останавливается до ручной проверки результата.
- При доставке из очереди и повторной отправке слушатели `RequestDelivery` вызываются после фиксации итога. Для изменения заявки загрузите её по ID через свой менеджер сущностей и явно сохраните. Исключения слушателей записываются в журнал. Ожидающее событие сохраняется для повтора воркером Messenger или командой `itk:requests:recover`, без повторной отправки провайдеру. Свои слушатели должны быть идемпотентными, поскольку падение после успешного слушателя может привести к повторному вызову.
- Доставка и синхронный повтор уже зафиксированной заявки сохраняют итог на независимом соединении с фиксацией, если вызывающий код управляет транзакцией или отключил autocommit. Новая заявка и задания очереди остаются в транзакции вызывающего кода. Отправка провайдеру начинается только после её фиксации.
- `GET /admin/api/collections/{col}` теперь всегда возвращает `{ items, total, page, perPage, facets, metrics }`. Старый ответ плоским массивом удалён, в том числе у запросов без параметров. Читайте `response.items` и загружайте нужные страницы через `page`, `perPage` и `total`. Размер страницы по умолчанию 50, если не настроен иначе, максимум 200. `envelope` принимается для совместимости.
- `Mcp\AbstractMcpTool::locale()` теперь нестатический. Внутри методов экземпляра работают `self::locale($args)` и `$this->locale($args)`. Перенесите вызовы из статического контекста в метод экземпляра. Если класс сайта переопределяет `locale()` как `static`, уберите `static` из переопределения, иначе PHP не загрузит класс.
- При подключении `itk_cms.locales` у `main_locale` обрезаются пробелы и понижается регистр; код должен состоять из 2 или 3 строчных латинских букв и входить в список. Без `locales` прежнее значение сохраняется. Если на работающем сайте основной код нестандартный (`RU`, ` ru ` или `pt-BR`), выберите поддерживаемый код и до включения `locales` вручную перенесите сохранённые языковые значения и ключи JSON. Изменение конфига само по себе не переносит содержимое. Региональные метаданные задавайте в `html_lang` / `og_locale`.

Пример PostgreSQL ниже меняет точный старый код `RU` на `ru`. Подставьте оба значения по данным сайта; сначала проверьте резервную копию и разрешите конфликты, когда старый и новый коды уже сосуществуют (переводы страниц, настройки, меню, записи коллекций и исторические снимки). Обновления JSON намеренно пропускают строку, в которой уже есть новый ключ. Сохраните общие настройки (`locale = '*'`) и SEO-правила для всех языков (`locale IS NULL`). Отдельно проверьте таблицы и интеграции сайта. Это пример ручного обслуживания, а не миграция бандла.

```sql
BEGIN;
UPDATE itk_page_translation SET locale = 'ru' WHERE locale = 'RU';
UPDATE itk_setting SET locale = 'ru' WHERE locale = 'RU';
UPDATE itk_revision SET locale = 'ru' WHERE locale = 'RU';
UPDATE itk_seo_rule SET locale = 'ru' WHERE locale = 'RU';
UPDATE itk_menu_area
SET items = (items - 'RU') || jsonb_build_object('ru', items->'RU')
WHERE items ? 'RU' AND NOT (items ? 'ru');
UPDATE itk_collection_item
SET translations = (translations - 'RU') || jsonb_build_object('ru', translations->'RU')
WHERE translations ? 'RU' AND NOT (translations ? 'ru');

-- Исторические снимки удалённых целиком страниц и записей коллекций.
UPDATE itk_revision
SET snapshot = jsonb_set(snapshot, '{versions}',
    ((snapshot->'versions') - 'RU') || jsonb_build_object('ru', snapshot->'versions'->'RU'))
WHERE snapshot->'versions' ? 'RU' AND NOT (snapshot->'versions' ? 'ru');
UPDATE itk_revision
SET snapshot = jsonb_set(snapshot, '{translations}',
    ((snapshot->'translations') - 'RU') || jsonb_build_object('ru', snapshot->'translations'->'RU'))
WHERE snapshot->'translations' ? 'RU' AND NOT (snapshot->'translations' ? 'ru');
COMMIT;
```

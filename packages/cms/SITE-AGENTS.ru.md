# Правила для ИИ-агента, который делает сайт на ITK CMS

Этот сайт построен на ITK CMS, Symfony-бандле `itk/cms`. Ядро бандла общее для всех сайтов на этой CMS. Его документация это [README.ru.md](README.ru.md) пакета, рядом с этим файлом. В сайте это `vendor/itk/cms/README.md`.

## Предлагайте возможности ядру

Если сайту нужна возможность, которой в ядре нет, и она пригодится другим сайтам, предложите её ядру pull request'ом. Не делайте её только для этого сайта. Мейнтейнеры ITK CMS посмотрят pull request. Если они его примут, возможность получат все сайты на CMS.

Pull request открывается в репозитории [it-koval/cms](https://github.com/it-koval/cms). Код бандла лежит в нём в `packages/cms`. Репозиторий `it-koval/cms-bundle` заполняется автоматически и pull request не принимает.

## Как решить, где делать доработку

1. **Сначала найдите точку расширения.** Их в ядре много, и каждую описывает README пакета: поля, классы-ресурсы, хуки и события, действия, фильтры, виды списка, меню админки, расширения, настройки в коде, свои инструменты MCP и генераторы `itk:make:*`. Если задача решается через одну из них, решайте её в коде сайта.
2. **Код только этого сайта остаётся в сайте.** Вёрстка, шаблоны, секции, коллекции, бизнес-правила клиента и интеграции, нужные одному сайту, пишутся в `src/`, `templates/` и `config/` сайта.
3. **Доработка ядра идёт pull request'ом.** Сюда относятся точка расширения, которой не хватило в шаге 1, ошибка ядра, общая возможность (новый тип поля, команда, проверка или настройка) и новая системная зависимость ядра.

Если не уверены, общая ли это возможность, спросите человека, который поставил вам задачу.

## Не обходите ядро

- Не правьте файлы в `vendor/itk/cms`. Следующий `composer update` сотрёт правку.
- Не копируйте классы, шаблоны или JavaScript ядра в сайт, чтобы поправить копию. Копия перестанет получать исправления ядра.
- Не используйте внутренние классы ядра. Классы с пометкой `@internal` в докблоке не являются публичными и могут измениться в любом минорном релизе. Это относится и ко всему, что README называет внутренним. Если без такого класса не обойтись, ядру не хватает точки расширения. Предложите её pull request'ом.
- Не меняйте таблицы ядра (`itk_*`) миграциями сайта. Схему ядра меняют только миграции бандла.

## Как подготовить pull request в ядро

- Следуйте [CONTRIBUTING.md](https://github.com/it-koval/cms/blob/main/CONTRIBUTING.md). Сначала напишите тест, который без правки падает. Запустите проверки PHP и админки. Добавьте запись в [CHANGELOG.md](https://github.com/it-koval/cms/blob/main/CHANGELOG.md). Добавьте заметку в [UPGRADE.md](https://github.com/it-koval/cms/blob/main/UPGRADE.md), если меняется публичный API. Опишите новую возможность в README. Обновите комплект Docker, если появилась системная зависимость.
- Один pull request решает одну задачу. Опишите сценарий сайта, который упёрся в ядро, что меняется и как вы это проверили.
- Не включайте в pull request данные клиента: тексты, адреса, ключи и выгрузки базы. Описывайте сценарий обобщённо.
- Если вы не можете открыть pull request сами, подготовьте ветку или патч с описанием и передайте человеку, который поставил задачу.

## Пока pull request не принят

Сайт может ждать релиза или сделать временный обход в своём коде. Обход не копирует код ядра. Пометьте его комментарием со ссылкой на pull request, например `// временно, до it-koval/cms#123`. Удалите обход, когда сайт обновит пакет до версии с доработкой.

## Отчёт

В отчёте о задаче перечислите pull request'ы в ядро, которые вы открыли или подготовили, и временные обходы, которые их ждут.

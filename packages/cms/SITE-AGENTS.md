# Правила для ИИ-агента, который делает сайт на ITK CMS

Сайт построен на ITK CMS: Symfony-бандле `itk/cms`. Ядро общее для всех сайтов на этой CMS. Его документация лежит рядом с этим файлом, в `README.md` пакета (у сайта это `vendor/itk/cms/README.md`).

## Главное правило

Если сайту нужна возможность, которой в ядре нет, и она пригодится не только этому сайту, предложите её ядру pull request'ом. Не делайте её только для себя. Мейнтейнеры ITK CMS посмотрят PR и, если примут, возможность получат все сайты на CMS.

PR открывается в репозиторий [it-koval/cms](https://github.com/it-koval/cms), код бандла лежит в нём в `packages/cms`. Репозиторий `it-koval/cms-bundle` заполняется автоматически, PR в него не принимаются.

## Как решить, где делать доработку

1. **Найдите точку расширения.** Ядро даёт их много, каждая описана в README пакета: «Поля», «Разделы-классы», «Хуки и события», «Действия», «Фильтры», «Виды списка», «Меню админки», «Расширения», «Настройки в коде», «Свой инструмент» в разделе MCP и генераторы `itk:make:*`. Если задача решается через одну из них, решайте в коде сайта.
2. **Код только этого сайта остаётся в сайте.** Вёрстка, шаблоны, секции, коллекции, бизнес-правила клиента, интеграции, нужные одному сайту: всё это пишется в `src/`, `templates/` и `config/` сайта.
3. **Доработка ядра идёт PR'ом.** Сюда относятся новая точка расширения, которой не хватило в шаге 1, ошибка ядра, общая возможность (новый тип поля, команда, проверка, настройка) и новая системная зависимость ядра.

Если не уверены, общая ли это возможность, спросите человека, который ставит вам задачу.

## Чего не делать

- Не правьте файлы в `vendor/itk/cms`. Следующий `composer update` сотрёт правку.
- Не копируйте классы, шаблоны или JS ядра в сайт, чтобы поправить копию. Копия перестанет получать исправления ядра.
- Не обходите ядро через его внутренние классы. Классы с пометкой `@internal` в докблоке и всё, что README называет внутренним, может измениться в любом релизе. Если без такого класса не обойтись, значит, ядру не хватает точки расширения, и её нужно предложить PR'ом.
- Не меняйте таблицы ядра (`itk_*`) миграциями сайта. Изменение схемы ядра делает миграция бандла.

## Как оформить PR в ядро

- Следуйте [CONTRIBUTING.md](https://github.com/it-koval/cms/blob/main/CONTRIBUTING.md): сначала тест, который без правки падает; проверки PHP и админки; запись в `CHANGELOG.md`; заметка в `UPGRADE.md`, если меняется публичный API; раздел README для новой возможности; Docker-комплект, если появилась системная зависимость.
- Один PR решает одну задачу. Опишите в нём, какой сценарий сайта упёрся в ядро, что меняется и как вы это проверили.
- В PR не попадают данные клиента: тексты, адреса, ключи, выгрузки базы. Пример сценария пишите обобщённо.
- Если у вас нет доступа, чтобы открыть PR, подготовьте ветку или патч с описанием и передайте человеку.

## Пока PR не принят

Сайт может ждать релиза или сделать временный обход в своём коде. Обход не копирует код ядра, помечен комментарием со ссылкой на PR (`// временно, до it-koval/cms#123`) и удаляется, когда сайт обновит пакет до версии с доработкой.

## Отчёт

В отчёте о задаче перечислите PR в ядро, которые вы открыли или подготовили, и временные обходы, которые ждут этих PR.
